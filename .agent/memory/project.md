# Durable project memory

## Product scope
WellCosting Pro is a tenant-aware SaaS foundation. The current increment covers authentication, user/role/permission CRUD, assignments, workspace and module dashboards, an audit trail, Master Data Management for UOM, Currency, Phases, Hole Sections, Activities, Services, Vendors, and PO/SO Orders (with attachments and amendment revisions), plus Rig & Well Management, AFE Management (AFE register, cost estimation, approvals), Daily Cost Management (daily cost sheets, whole-well cost analysis), and the Reports module (well-wise cost comparisons and Consumption/Losses reporting from existing permission-scoped APIs). Report amounts remain grouped by currency, and exports are audited through the source modules. Project domain entities and workflows beyond these modules are **not implemented yet**.

## Standing product conventions (mandatory for every module and page)
These are cross-cutting requirements. Every new page, module, and feature must comply; code review must reject violations. They apply to User Management, Master Data Management, Business modules, Report modules, Back-up modules, Auditing modules, and anything added later.

1. **Audit everything.** All user actions on all pages (create, update, delete, assign, import, export, sign-in/out, admin changes) are written to the audit trail with actor, action, entity, summary, IP and timestamp. Audit records are read-only to normal users. Every page ships with auditing by default.
2. **Light and dark themes.** Every screen must work in both Light and Dark themes, with matched font colours, borders, backgrounds and chart/grid palettes. The user selects the theme (persisted per browser); defaults to the system preference.
3. **Top navigation only.** Primary navigation is a top-side horizontal bar with dropdown menus grouped by module. No side navigation drawers for primary nav.
4. **No JSON in the database.** Never store JSON/JSONB blobs, serialized documents, or key-value payload columns. Use conventional, typed, column-wise table design (one column per business attribute). API responses may shape JSON; persistence must not.
5. **Pagination everywhere lists appear.** Every page listing data uses pagination with page-size options **20 / 50 / 100** (default 20), both on server-driven lists and in grids.
6. **Easy and advanced filtering.** List pages offer a quick (easy) search plus an advanced filter panel that can filter on any available column/criterion (equals, contains, ranges, etc.). Date and date-range filters are kept as a separate, dedicated control group (from/to pickers), distinct from the general filters.
7. **Import and export.** Data list pages provide import from Excel-family files (**.xlsx and .csv**) and export to **.xlsx, .csv and PDF**, with preview before import and row-level errors shown inline. (Endpoints/pages that cannot support import must at least support export.)
8. **Module-wise dashboards.** Each module (User Management, Master Data Management, Business modules, Report modules, Back-up modules, Auditing modules, …) gets its own dashboard/summary page showing module KPIs and recent activity. Modules are still being added; do not represent unbuilt modules as shipped.
9. **Navy Blue & White enterprise theme.** Professional Navy Blue and White palette (light) and navy-based dark palette; no green branding, no unnecessary animations, no decorative motion, no emojis. Enterprise-grade, business-oriented, well-structured layouts.
10. **Alerts near the data.** Error messages, warnings and confirmations appear next to the responsible input/field or as dialog pop-ups — never as detached global banners. Destructive actions confirm via dialog.
11. **RBAC on every page.** Every page is created with RBAC controls by default; visible actions are permission-gated and the admin user controls access through roles/permissions. The API remains the authorization authority.
12. **Pop-ups close only via Cancel.** Any data-entry pop-up (create/edit/assign/delete confirmation, import, change password, and any future dialog) must NOT close when the user clicks outside it (backdrop) or presses Escape, and has no X/close icon. Only the **Cancel** button closes it (a successful save/import also closes it). Implemented once in `FormDialog` (`frontend/src/components/Common.tsx`), which `ImportDialog` and all pop-ups reuse; do not pass `onClose` to a raw MUI `Dialog` or add backdrop/Escape close handlers. Panels that are not a single submit form (the PO/SO attachments and revision-history panel) use `PanelDialog` from the same file, which enforces the same rule with a footer button instead of a submit action.
13. **Per-record actions and bulk selection.** Every mutable master-data/business-record row exposes Edit and Delete actions for users authorized to use them; data tables include a checkbox per row and a header checkbox to select all matching entries for bulk actions. Gate each action by RBAC and keep immutable/security-protected identity and RBAC records subject to their existing safeguards.
14. **Soft delete first; purge only from Deleted Entries.** A normal Delete action on master/business data must soft-delete the record and move it to a Deleted Entries view. Never permanently delete an active master/business record. Restore and permanent-delete actions are offered from Deleted Entries; permanent deletion requires an explicit confirmation dialog. Audit soft delete, restore, and permanent deletion.
15. **Never lose entered data — unsaved-changes protection everywhere (2026-10-13).** Every data-entry surface must protect what the user typed before it disappears. This is mandatory for every existing page and every future module. (a) Pop-ups: `FormDialog` (`frontend/src/components/Common.tsx`) detects any input in the dialog (typing, option picks, toggle changes; pages may also pass an exact `dirty` prop, computed with `useFormDirty`) and, when the user clicks Cancel, asks first: "Save & close" runs the dialog's normal save path (a validation failure keeps the dialog open with the messages next to the fields), "Discard changes" closes deliberately, "Continue editing" stays. Confirmation-only dialogs (no inputs) are never dirty and keep their simple Cancel. (b) Full-page editors (AFE estimate, daily cost sheet, and every future entry page) call `useUnsavedChangesGuard({ when, onSave })` from `Common.tsx`, which intercepts in-app navigation and the back button (React Router `useBlocker`, which is why `main.tsx` uses `createBrowserRouter`) and tab close/reload (`beforeunload`), offering "Save & continue" / "Discard changes" / "Continue editing". Reuse these two primitives; do not hand-roll new close guards. (c) A workspace default currency (`currencies.is_default`, exactly one active default per workspace, set from Master Data → Currency) is preloaded by every currency dropdown: `MasterSelect` preloads it for new priced records, and the AFE reference payload carries `is_default` so AFE line dialogs, the bulk estimate and the standard-currency picker start from it. Keep these behaviours intact when adding modules.

## Other Managements (2026-10-13)
- The former top-level **Auditing** dropdown is now **Other Managements**: Overview (`/other-management`, visible to anyone with `audit:read` or `database-browser:read`), **Audit Log** (`/other-management/audit`; the old `/audit` path redirects) and **Database Browser** (`/other-management/database`, table page at `/other-management/database/:tableName` with Data and Structure tabs).
- Database Browser is **read-only and tenant-scoped**. Tables are reflected from the live database (`backend/app/services/database_browser.py`). A table is listed only if it can be tied to the caller's workspace: directly by `organization_id`, or through a foreign-key chain (for example `user_roles` → `users`). Tables that cannot be tied to a workspace are not listed. `alembic_version` and `refresh_sessions` are hidden. Columns matching password/secret/token/hash and the lockout counters are never returned, sorted, filtered or exported.
- Permissions: `database-browser:read` (catalogue, structure, rows) and `database-browser:export` (full CSV download and grid/structure exports). Owners receive both; migration `4a6d2e9c8b17` backfills existing workspaces. Holders of `database-browser:read` can see every business row of the workspace, so grant it deliberately.
- Grid previews are capped at 5,000 newest rows (the grid is client-side, so the standard quick search, advanced filters, date range, 20/50/100 paging and CSV/XLSX/PDF export all apply to the rows on screen). `GET /database-browser/tables/{name}/download.csv` streams every row (limit 250,000) for Power BI. Each export is audited through `POST /database-browser/export-audit` or, for downloads, in the same request.
- CSV cells that begin with `= + @` or a tab/CR are prefixed with an apostrophe to block spreadsheet formula injection.

## Architecture decisions
- React 19 + MUI 7 + AG Grid 35 + ECharts 6 + Vite, routed in `frontend/src/App.tsx`. MUI light/dark themes built in `frontend/src/theme.ts`, toggled via `frontend/src/context/ThemeContext.tsx` (persists to `localStorage`, sets `data-theme` on `<html>` for CSS variables).
- Navigation is the top bar in `frontend/src/components/Layout.tsx`: module dropdown menus, theme toggle, account menu. No sidebar.
- Design tokens are centralized in `frontend/src/designSystem.ts` (navy ramp, surfaces, semantics, type scale, spacing, radii, shadows, motion, AG Grid skin), composed into `theme.ts` and mirrored as `--wcp-*` variables in `styles.css`. Pages must not hardcode colours, radii or font stacks; status chips read the CSS variables because AG Grid cell renderers may not receive the React theme context. See `.agent/memory/design-system.md`.
- `frontend/src/components/DataTable.tsx` is the standard list surface: quick search, advanced filters (per-column rules + separate date & date-range group), AG Grid pagination 20/50/100, and Export (CSV/XLSX/PDF) via `frontend/src/lib/export.ts`. `frontend/src/components/ImportDialog.tsx` is the standard import flow (xlsx/csv parse, preview, row-level errors).
- FastAPI + SQLAlchemy 2 + Alembic; PostgreSQL for Compose/deployment, SQLite only for lightweight local development and tests.
- Organization IDs scope all RBAC and audit records; never accept an organization ID in a management request. Authentication uses workspace slug + email + password.
- Access JWT stays in browser memory; rotating opaque refresh tokens are hashed in DB and sent as HttpOnly SameSite cookies. A password change revokes sessions and increments token version.
- API is the authorization authority. Client-side `can()` only hides controls. Owner role is immutable and assigned only by provisioning to prevent lockout. Nonowners cannot grant access they don't have.
- Capability keys use `resource:action`; baseline API capabilities are provisioned per organization, and custom capabilities are tenant data. Baseline includes `audit:read` for the Other Managements audit log and `database-browser:read`/`database-browser:export` for the Database Browser.
- **Audit trail is column-wise** (`audit_logs` table: actor, action, entity_type, entity_id, entity_label, summary, ip_address, user_agent, created_at — never a JSON payload column). `app/services/audit.py` records entries in the same transaction as the change; `app/api/audit.py` serves the paginated, filterable `/audit` list behind `audit:read`.
- **Master Data Management** is an organization-scoped module with five typed tables (`uom`, `currencies`, `phases`, `hole_sections`, `activities`), shared lifecycle timestamps, per-workspace unique codes, and `is_deleted`/`deleted_at` soft-delete fields. `/api/v1/master-data` maps those typed attributes to a common API record shape; its dashboard, tabs, Deleted Entries view, row actions, and bulk actions follow this app's MUI/AG Grid structure, not the legacy UI. The `master-data:*` capabilities guard reads, writes, restore, purge, import, and export; migrations backfill those permissions for existing owners. Permanent deletion is accepted only for already soft-deleted rows. Every module action is written to the typed audit trail.
- **Services** are a typed register within Master Data Management (`app/models/service_master.py`, `app/api/service_master.py`, `frontend/src/pages/Services.tsx`). `services` stores a workspace-unique manually entered code (trimmed and upper-cased), service name, category (Drilling Services or Completion Services), provider type (In House Services or Third Party Services), vendor FK, description, and common soft-delete/audit lifecycle columns. Service names are case-insensitively unique per workspace, including deleted rows; both provider types require a non-deleted workspace vendor on create/update/import/restore. Historical unassigned in-house services remain readable until explicitly assigned; no vendor is invented during migration. The service dashboard summarizes categories and provider types; list actions use the shared import preview, filtering, pagination, and CSV/XLSX/PDF export. Imports require service_code and vendor_code, upsert/restore by code, accept legacy Inhouse/3rd Party labels and default old rows without a category to Drilling Services. Vendors referenced by active services cannot be soft-deleted; service assignments must be purged before their vendor can be purged. The API reuses the `master-data:*` capabilities and includes Services in the Master Data overview and Deleted Entries page.
- **Vendors and PO/SO Orders** are the commercial tabs of Master Data Management (`app/models/vendor_master.py`, `app/api/vendor_master.py`, `frontend/src/pages/Vendors.tsx`, `frontend/src/pages/PoSoOrders.tsx`). Vendors are added first (`vendors`: code unique per workspace, vendor type (Inhouse or Third party), category, contact, e-mail, phone, website, country, tax/registration no., address, status active/inactive/blocked, credit terms; the category list includes Completions beside Drilling); a blocked vendor is refused new orders, and a vendor with active orders or active Services cannot be soft-deleted or purged until those records go. Orders (`po_so_orders`) carry **no prices or values** — the attached scan is the record. Each order number forms an amendment chain: revision 0 is the original, `parent_order_id` + `revision_number` (server-assigned) hold the lineage, `is_current` marks the revision to quote, and renaming an order number renames the whole chain. Documents (`po_so_documents`) store several files per revision with kind/label/notes, SHA-256 checksum (duplicates inside one order are refused), uploader, and the revision they were attached to; removal is soft (recoverable from the same panel) and only purge is permanent. Bulk attach matches `<ORDER NUMBER>[_Rev<N>].pdf` file names to orders.
- **Attachments live in the workspace database** (`po_so_documents.content`, a deferred `LargeBinary`, capped by `DOCUMENT_MAX_SIZE_MB`, default 15) because the deployed API filesystem is ephemeral. This is a binary payload, not a JSON document, so the column-wise rule still holds; every other attribute is a typed column. Moving to object storage later means swapping `_store_document`/`download_document` only.
- **Document custody is separately grantable**: `master-data:document-upload`, `master-data:document-download`, `master-data:document-delete` join the existing `master-data:*` capabilities (provisioned for new workspaces, backfilled to owners by the vendors migration). Downloads are audited too, so the trail shows who opened which PO/SO copy.
- Migrations are explicit Alembic revisions. Do not use `create_all` in the app runtime.
- The owner account is the platform administrator. On a new device the database is empty, so at startup the API detects the missing owner and asks the operator to create one (`app/bootstrap.py` + prompts in `app/services/console.py`, provisioning in `app/services/provisioning.py`, schema state in `app/core/migrations.py`). It never invents credentials, never writes to an existing tenant, never creates tables behind Alembic and never blocks a non-interactive process; `SEED_*` variables cover unattended first boots and `BOOTSTRAP_ADMIN_ON_STARTUP=false` disables the check. `python -m app.seed` is the same flow as a CLI, `--check` exits 0 admin present / 1 missing / 2 unmigrated / 3 failed.

## Daily Cost Management
- **Register is not a dashboard (2026-10-13, user requirement).** The daily register contains navigation/new-sheet/print actions, filters and sheet rows only. No workspace-wide KPIs/charts, recent activity or aggregate budget UI, and no cumulative column derived from filtered rows. It no longer calls the legacy overview API; that endpoint remains for compatibility, not for display. This is an explicit exception to the generic module-dashboard convention: cost KPIs belong to individual daily sheets or an explicitly selected well. The analysis landing page must not silently choose a well; stale requests may not replace the selected well's summary. Further analysis configuration remains open pending user requirements.
- **Complete model-based print reports (updated 2026-10-23).** `DailyCostPrintSheet.tsx` renders into a body portal with a dedicated named **A4 landscape / 4 mm margin** page. Page 1 follows `MODEL REPORTS/COSTING DAILY REPORT FORMAT.jpg` and `MODEL REPORTS/MODEL REPORT.pdf`: report/well/rig identity; the milestone wording saved with the well's progress record (default **Spud date & time**, editable per well scope in the daily sheet, never at print time); the lead / lag saved on the daily sheet and printed as `(LEAD: n days)` / `(LAG: n days)` at the end of the title, or `(LEAD/LAG: 0 days)` when neither is recorded; section planned/current depth; Time Position (**Planned, Actual, Actual against Planned Activities = elapsed actual minus NPT/UPA duration, NPT, UPA**); cumulative service/consumable/tangible and AFE positions; and NPT/UPA summaries. Mixed AFE currencies remain separate, export audits/RBAC/tenant boundaries are unchanged, and no schema or pricing behavior changes. `DailyCostBulkScopeDialog.tsx` also lets checked service lines keep or receive one shared actual depth + depth unit and charged quantity + quantity unit alongside Activity/scope; validation matches the normal line editor and edits remain draft until save. - **Column-wise by design.** `daily_cost_entries` (header: rig/well/AFE snapshots, cost date, status, remarks, group totals, UPA/NPT totals, warning count, soft delete) plus four typed line tables (`daily_cost_service_lines`, `daily_cost_consumable_lines`, `daily_cost_tangible_lines`, `daily_cost_other_expense_lines`). Locked `daily_cost_baselines` and `daily_cost_baseline_*` rows snapshot the AFE total, FX rates, catalogue revisions, service rate cards, section/phase plan and budget lines. Every line carries its own activity/section/phase/sub-activity, classification (Planned/UPA/NPT), vendor/party, native currency + rate + amount, standard amount, rate source and budget-key link. No JSON columns anywhere.
- **Rate immutability is the core rule.** A daily sheet prices only from its baseline snapshot or a justified per-line `override_rate` + `override_reason`. Later Master Data revisions never flow backwards into an existing sheet.
- **PostgreSQL row locks must stay single-table (production 503 fix).** Every daily-cost write locks a row, and the models load several many-to-one references with `lazy="joined"`. Locking an entity-shaped (or eager-loading) SELECT therefore emits `LEFT OUTER JOIN … FOR UPDATE`, which PostgreSQL refuses with `FOR UPDATE cannot be applied to the nullable side of an outer join` (SQLSTATE 0A000) — every `POST /daily-cost/entries`, save, submit, reopen, delete and restore answered 503 while SQLite (which ignores the clause) kept the suite green. `_lock_row_id(db, model, *criteria)` now locks `model.id` only — single-table by construction, whatever loader strategies the models declare — and the row is then read with its usual eager loading in the same transaction (`_get_entry`, `_ensure_rate_baseline`/`_rate_baseline_by_id`, `_ensure_afe_baseline`/`_baseline_for`). The same rule applies to every module: never add `joinedload`/`lazy="joined"` to a row-locked statement, and prefer the lock-the-key-then-load shape.
- **PostgreSQL GROUP BY is strict.** The whole-well budget reconciliation selected `activity_name`/`party_name` while grouping only by `(cost_group, budget_key)` (SQLite picks an arbitrary bare row; PostgreSQL raises `GroupingError`, so `GET /daily-cost/wells/{id}/cost-summary` returned 500). The labels are now `func.min(...)` aggregates, keeping one deterministic name per budget key on both dialects.
- **500 hardening.** `import_daily_cost()` normalises `charging_basis` through `BASIS_ALIASES` (case-insensitive `day rate`/`dayrate`/`day`/`per service rate`/… ) and validates the quantity unit, instead of indexing raw strings; `_flush()` and `_commit()` map `IntegrityError`→409, `DataError`→422 and other SQLAlchemy/database failures→503 with rollback and logging; baseline races reuse the winning immutable snapshot where possible; create/save/read-back boundaries turn malformed legacy AFE data into actionable 422/503 responses; `reference_data()` skips unusable AFEs instead of failing; `_money()` raises 422 past `MONEY_LIMIT = 9999999999999999.99` (mirrors Numeric(18,2)). `app/main.py` adds a JSON `http_error` handler and a global `unexpected_error` handler that logs the traceback and returns 500 with a short `reference` id; the daily-cost 503 detail now carries the same kind of reference (`[xxxxxxxxxxxx]` in `Daily cost <operation> failed with a database error`), so a user report can be matched to the exact failing statement in the Render logs. Net effect: daily-cost create/edit database and data-boundary failures are no longer leaked as opaque 5xx responses.
- **Pricing and operator guardrails.** Day Rate `Mobilization`, `Demobilization` and `Fixed Charge` lines are unit-priced events: the positive recorded quantity is retained for operations, but the selected rate is charged exactly once. The day-sheet grid and line dialog show the same semantics. The register validates real calendar dates, warns/prevents an in-register duplicate well/AFE/date, offers an Open existing action, and refreshes after a server-side duplicate conflict; save is disabled while preview is pending/invalid and Retry preview actually re-runs the request.
- **Entry rules: Activity-derived classification, mandatory well sub activity, split services.** Classification (Planned/UPA/NPT) is **not** entered on a daily cost line — the Master Data Activity already serves that job. `classify_activity()` (`app/services/daily_cost.py`) derives it from the activity code/name (NPT / non-productive → NPT, UPA / unplanned → UPA, else Planned; mirrored in the frontend by `deriveClassification()` in `lib/dailyCost.ts`), and it is stored on each priced line so `upa_total`/`npt_total`, warnings and the Planned/UPA/NPT analysis factor keep working. `classification` is removed from the line input schemas (extra keys are rejected) and from the import template; a legacy `classification` column in imported files is ignored. Configuring the well sub activity in Rig & Well Management is mandatory for daily cost entry: `create_entry` rejects a well with no active sub activities (message points at Rig & Well Management), and every service/consumable/tangible line must carry a `sub_activity_id` belonging to the well and the selected Activity (`_get_sub_activity` is non-optional). On the same date for the same well, the same service may be recorded multiple times **only** under different sub activities (e.g. 18h/3h/3h across sub activities); `_reject_duplicate_service_sub_activity()` rejects a repeated service + sub activity pair on save/preview/import. The day-sheet grid shows a SUB ACTIVITY column (the entry CLASS column was removed), and the line dialog enforces mandatory sub activity, no-duplicate-service, and UPA/NPT party/manual-rate rules (driven by the derived classification) next to the fields; the register's create dialog blocks wells without configured sub activities.
- **Other expenses (LIH and similar) are a fourth cost group that is deducted from the AFE (2026-10-13, user requirement).** Unexpected charges — Lost In Hole, hole problems, fishing/recovery, side track, equipment damage, third-party claims, penalties, misc — are captured in `daily_cost_other_expense_lines` instead of being smuggled into Services/Consumables/Tangibles. The user's three explicit decisions: (1) its own cost group whose total **is** part of the day's cost, with AFE reconciliation `Total AFE − (Services+Consumables+Tangibles) − Other Expenses = remaining`; (2) a **fixed picklist** of expense types (no master-data register, no free-text category — the deduction rule depends on the type and an open list would let a mis-typed category change the AFE position; each row snapshots `expense_type_label` and keeps optional free text in `expense_description`); (3) the amount is **quantity × entered unit rate** in the line currency, converted with the locked AFE FX like every other line (no catalogue lookup and no `override_rate` — a daily override is meaningless where there is no baseline rate, so the schema rejects it and `rate_source = other_expense`). **Remarks are mandatory** (>= 3 non-blank chars, `OTHER_EXPENSE_MIN_REMARKS`) because the remark is the only narrative explaining the charge; enforced twice — in the Pydantic input validator *and* as `CHECK (LENGTH(TRIM(remarks)) > 0)` on the table — because the API is not the only writer. The lines still carry the full operational scope (Phase, Activity, Sub-Activity, Hole Section, vendor/party) and derive Planned/UPA/NPT from the Activity as usual, so they classify, filter, group and audit identically; `planned` for the group is always 0.00 and `budget_key = other:<TYPE>` makes the expense type the reconciliation row. A save that changes the deduction writes its own audit row (`action = other_expense`) next to the save's, and the sheet carries the `other-expenses-deducted` warning (`_warnings`); `comparison.tracked_actual_to_date` + `other_expenses_to_date` keep both halves visible while `actual_to_date`/`balance` stay the sums everything else reconciles against, so with no deductions every existing figure and test invariant is untouched. Import accepts `Line Type = Other` with spoken aliases (`OTHER_EXPENSE_TYPE_ALIASES`, `lost in hole` → `LIH`); missing remarks/rate or an unknown type are row errors, never a 500. Propagation is deliberately everywhere: entry roll-up (`other_expenses_total`), register, sheet, analysis, overview groups (the group is always present with planned 0), well summary totals/`cost_group`+`item` factor cuts/AFE positions/`budget_lines`/warnings, and the printable sheet's section 6 plus an AFE-register column. - **Meaning of the milestones.** "Progress Completed Date & Time" is the final instant of the whole progress: drilling operations completion for a drilling well, completion operations completion for a completion well (`progress_label` in the API). For a completion well the pair lives on the completion scope with the same rules.
- **Day math (corrected 2026-10-21).** Actual days = (progress completion − spud) once completion is entered — the exact completion timestamp supersedes cost-sheet dates, stops the count for that well-scope and freezes the variance. Before completion, the count ends at the close of the **last saved cost-sheet date for that scope**, never the current/print date. A filtered well report uses its last included sheet; with no sheet there is no actual-day value yet. Fractional at three decimals, half-up: spudded 19/10/2026 10:00 hrs with a 19/10/2026 cost sheet counts **0.583 days**. Planned days per scope = the latest *approved* `WellPlanAdjustment.planned_days_after`, else the configured `well_phases` day total (same definition as the Business Dashboard); difference = actual − planned.
- **Entry surface.** `WellProgressPanel` (`frontend/src/components/daily-cost/WellProgressPanel.tsx`) sits at the top of the daily cost sheet (its AFE's scope, counted to the sheet's cost date) and at the top of Well Cost Analysis (both scopes, counted to each scope's last included cost-sheet date); datetime-local inputs, inline error alerts, per-panel Save. The sheet folds unsaved milestone edits into its `useUnsavedChangesGuard`; the analysis page gets its own guard. Prints: each day sheet section in `DailyCostPrintSheet` shows spud, completion, actual/planned/difference.
- **API.** `GET/PUT /api/v1/daily-cost/wells/{well_id}/progress` (read: `daily-cost:read`; write: `daily-cost:update`; audited as `entity_type="well_progress"`). The day payload (`DailyCostDayOut.progress`), the well summary (`DailyCostWellSummary.progress` + `totals.spud_actual_days/spud_days_variance`) and every cost-report row carry the milestones. Validation: spud can be entered once and then only **edited, never cleared**; completion requires the spud, must not precede it; no milestone may be more than a day in the future; clearing a completion resumes the count. Unknown fields rejected (`extra="forbid"`).
